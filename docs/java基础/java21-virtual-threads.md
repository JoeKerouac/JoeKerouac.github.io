# 聊聊 Java 21 虚拟线程——我为什么觉得它对业务开发没那么大用

前两天跟同事聊到 Java 21 的虚拟线程，聊到了有没有必要为了这个升级JDK。我个人的看法是，虚拟线程确实是个好东西，但要说它能改变我们日常写业务代码的方式，我持保留意见。

这篇文章算是把我的想法整理一下，核心观点先亮出来：**虚拟线程在网关、代理这类中间件场景下确实有价值，但对于大部分业务开发来说，它解决的问题我们早就有成熟方案了。**

## 先说说虚拟线程到底干了什么

简单讲，传统的 Java 线程（也叫平台线程）跟操作系统线程是一对一绑定的。一个 Java Thread 对应一个 OS 线程，创建成本高（栈内存默认 1MB），数量受限（通常也就几千个）。

虚拟线程打破了这个绑定关系。它是 JVM 自己调度的轻量级线程，多个虚拟线程共享少数几个平台线程（JDK 里叫 carrier thread）。虚拟线程跑到 IO 阻塞的地方，JVM 就把它从 carrier thread 上摘下来，让 carrier thread 去跑别的虚拟线程；IO 回来了再挂回去继续跑。单个虚拟线程只占几 KB 内存，理论上可以创建几百万个。

画个图比较直观：

```
  传统平台线程（1:1 绑定 OS 线程）         虚拟线程（M:N 模型）

  Platform Thread 1 ──> OS Thread 1       VThread 1 ─┐
  Platform Thread 2 ──> OS Thread 2       VThread 2 ─┼──> Carrier Thread 1
  Platform Thread 3 ──> OS Thread 3       VThread 3 ─┘
       ...                ...             VThread 4 ─┐
  Platform Thread N ──> OS Thread N       VThread 5 ─┼──> Carrier Thread 2
                                          VThread 6 ─┘
  每个线程 ~1MB 栈内存                         ...
  受 OS 线程数限制（几千个）              每个虚拟线程 ~几KB
                                         可以创建数百万个
```

左边是传统模型，一个 Java 线程绑一个 OS 线程，来几个请求就得开几个线程，开销大、上限低。右边是虚拟线程，大量虚拟线程复用少量 carrier thread，阻塞的时候自动切换，不浪费 OS 线程资源。

用法也很简单：

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> callRemoteService());
    executor.submit(() -> queryDatabase());
}
```

写起来跟普通线程池没区别，这也是它的设计目标——用同步的写法，拿到接近异步的并发能力。

## 为什么我觉得对业务开发帮助有限

说完虚拟线程是什么，下面聊聊我的核心观点。

### 想清楚一个问题：我们为什么需要那么多线程？

我觉得讨论虚拟线程之前，得先想清楚这个问题。

一个程序如果只做 CPU 计算，其实根本不需要很多线程——你有几个核，开几个线程就够了，多了反而因为上下文切换浪费性能。需要大量线程（远超 CPU 核数）的场景，**几乎都是因为 IO**。

想想看，不管是 RPC 调用、数据库查询、读写磁盘、还是调第三方 HTTP 接口，本质上都是 IO 操作。这些操作的特点是什么？**慢**。一次 RPC 调用动辄几毫秒到几十毫秒，一次数据库查询可能要几十毫秒，而 CPU 执行一条指令是纳秒级的。在等 IO 返回的这段时间里，CPU 是空闲的，所以我们需要更多的线程来填满 CPU 的等待时间——这就是线程数要大于 CPU 核数的根本原因。

所以，虚拟线程本质上解决的是：**在 IO 密集场景下，让你能开更多的"线程"来并发处理 IO 等待，而不受 OS 线程数量的限制。**

### 但这事，异步 IO 早就解决了

问题在于，Java 生态里处理 IO 密集场景的方案已经非常成熟了：

**NIO + 事件驱动**，从 Java 7 开始就有了，Netty 把它封装得很好。一个 EventLoop 线程就能处理成千上万个连接，不需要为每个连接分配一个线程。

**Reactor 模式**，Spring WebFlux、RxJava 这些框架在 NIO 的基础上提供了更高层的编程模型。写起来虽然不如同步代码直观，但并发能力完全不输虚拟线程。

也就是说，"IO 等待占线程"这个问题，NIO 和 Reactor **已经解决了**。它们的思路是反过来的——不是给你更多线程去等，而是压根不让线程去等。事件来了才处理，没事件线程就去干别的。

把这几种方案放一起看看：

|  | 线程池 | NIO / Netty | Reactor | 虚拟线程 |
|--|--------|-------------|---------|----------|
| 解决什么问题 | 线程复用，减少创建销毁开销 | 非阻塞IO，一个线程处理多连接 | 在NIO之上提供异步编程模型 | 同步写法 + 异步性能 |
| 编程模型 | 同步阻塞 | 回调 / 事件驱动 | 声明式链式调用 | 同步阻塞（看起来） |
| 代码复杂度 | 低 | 高 | 中高 | 低 |
| 调试体验 | 好 | 差 | 差（堆栈难读） | 好 |
| 并发上限 | 几百~几千 | 高 | 高 | 高（百万级） |
| 生态成熟度 | 非常成熟 | 成熟 | 成熟 | 发展中 |

可以看出来，虚拟线程的并发能力对标 Reactor，但编程模型对标线程池。说白了它提供了**第三条路**：你还是可以像以前一样写同步阻塞的代码，但底层帮你做了类似 NIO 的事情——虚拟线程阻塞时不会真的占着 OS 线程。

这确实很优雅。但问题是，如果你的项目已经用上了 Reactor 或者 Netty，或者你的业务并发量压根不需要这么高的并发能力——那这个优雅对你来说就没什么实际意义。

### 日常业务系统，线程池真的够用了

说实话，大部分后台业务系统的并发量没那么夸张。Tomcat 默认 200 个线程，在平均响应时间 200ms 的情况下，理论 QPS 能到 1000。大部分内部系统、管理后台、甚至不少 C 端接口，200 个线程绰绰有余。调一下线程池参数，三五百个线程，能覆盖绝大多数场景。

"线程不够用"这个问题，在业务开发中并没有那么普遍。你遇到性能瓶颈的时候，往往不是线程不够，而是数据库慢了、下游接口超时了、或者代码本身有性能问题。

### 数据库连接池才是真正的天花板

退一步讲，就算你用虚拟线程搞出了 10 万并发，然后呢？数据库连接池一般就 100~300 个连接：

```
  10万个虚拟线程
        |
        v
  ┌─────────────────────┐
  │  DB 连接池（300个）   │  <-- 真正的瓶颈在这里
  └─────────────────────┘
        |
        v
      数据库
```

你 10 万个虚拟线程排队等 300 个数据库连接，该慢还是慢。

虚拟线程解的是"线程不够"的问题，但业务系统的瓶颈在下游资源。更多的虚拟线程不但不能加速，万一下游没限流，搞不好还会把下游打挂——以前线程池 200 个线程，天然就限制了对数据库的并发，现在这层保护没了，你得自己加 Semaphore 来限流，反而多了一个心智负担。

### 还有些生态上的坑

虚拟线程不是拿来就能用的，目前还有一些实际问题：

**Pinning 问题**。虚拟线程在 `synchronized` 块里做 IO 操作时，会被"钉"在 carrier thread 上，没法切换，直接退化成普通线程。偏偏很多老库（JDBC 驱动、各种连接池）里面大量用了 `synchronized`。虽然可以换成 `ReentrantLock` 来解决，但这得等整个生态慢慢适配。

**ThreadLocal 问题**。业务代码里 ThreadLocal 用得很多——登录上下文、事务信息、trace id，都往 ThreadLocal 里塞。虚拟线程一旦量上去了，每个虚拟线程都带一堆 ThreadLocal，内存不是小数目。JDK 搞了个 `ScopedValue` 想替代 ThreadLocal，但现有代码迁移成本不低。

## 那虚拟线程适合什么场景？

说了这么多"不适合"，也得说说什么时候它是真的有用的。

**网关和代理类项目**，我觉得是虚拟线程最好的落地场景。网关的特点就是大量连接、逻辑简单、几乎全是 IO 转发。现在 Spring Cloud Gateway 这类框架底层是 Netty + Reactor，性能没话说，但代码写起来确实费劲——Reactor 的调试有多痛苦写过的人都知道，一个 `Mono.flatMap` 嵌套三四层，出了问题堆栈根本没法看。

如果用虚拟线程来写同样的网关逻辑，代码可以是完全线性的：接请求、转发、等响应、返回。可读性和可维护性甩 Reactor 好几条街，性能还差不多。对于**新建的网关/代理/中间件项目**，虚拟线程确实可以认真考虑。

另外像**批量并行调用**的场景也挺适合的，比如一个请求要同时调十几个下游服务然后聚合结果，用虚拟线程写起来就是起十几个虚拟线程各自去调，比 `CompletableFuture` 一堆 `thenCompose` 写起来舒服多了。

## 总结

| 场景 | 虚拟线程有价值吗 | 原因 |
|------|:---:|------|
| 网关/代理/中间件 | 有 | 大量IO、逻辑简单，虚拟线程能用同步写法替代Reactor |
| 批量并行IO调用 | 有 | 比 CompletableFuture 写起来干净 |
| 普通CRUD业务系统 | 不大 | 线程池够用，瓶颈在DB/RPC/磁盘IO等，不在线程，增加线程到一定数量后继续增加并不能提升吞吐量 |
| 已有 Reactor 架构的系统 | 不大 | 迁移成本高，收益不明显 |
| CPU密集型任务 | 没有 | 虚拟线程解决的是IO等待，对CPU计算没帮助，甚至过多的线程都没有意义 |

我的看法是，虚拟线程的定位其实很清楚——它是给那些"需要高并发IO、但又不想写 Reactor"的场景准备的。这个定位在网关/中间件层面很有意义，因为那里的 Reactor 代码复杂度确实是个痛点。但对于日常业务代码，由于我们需要大量线程的根因是 IO 等待，而 NIO 和 Reactor 早就把这条路趟过了，大部分业务系统甚至都走不到需要这些技术的并发量级。如果是新系统，可以考虑尝试下，如果是老系统，切换成本还是挺高的；

各位大佬们如果有不同的看法，欢迎讨论；
