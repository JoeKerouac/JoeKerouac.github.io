# RocketMQ 消息堆积排查：为什么一半队列无人消费？

## 背景

最近在生产环境在某个版本上线后，发现某个 Topic 出现了消息堆积，部分队列（MessageQueue）的消费进度一直没有推进，消息越积越多。经过排查发现，根本原因是**同一个 Consumer Group 下的不同 Consumer 实例订阅了不同的 Topic**，导致 Rebalance 分配出现问题，部分队列没有消费者实际消费。

> 实际上是两个不同的服务，共用了同一个消费者组，两个服务的订阅关系又不一致导致；

## 堆积原因分析

### 现象

监控系统告警某 Topic 消费延迟持续增大，通过 RocketMQ Console 查看发现：
- 该 Topic 有 4 个队列（Queue0 ~ Queue3）
- 其中 Queue2、Queue3 的消费 Offset 完全没有推进
- Queue0、Queue1 的消费正常

> 为什么是 4 个队列？RocketMQ 在客户端 `DefaultMQProducer` 中定义了 `defaultTopicQueueNums = 4`，当 Producer 发送消息到一个不存在的 Topic 时，会自动创建该 Topic 并使用这个默认值作为队列数。当然，实际生产中通常会通过运维命令或控制台手动创建 Topic 并指定队列数，队列数量可以根据业务吞吐量需要进行调整。

### 猜测

观察消费者组的情况，发现该 Consumer Group 下有 4 个消费者实例，但并非所有实例都订阅了这个 Topic。其中 2 个实例只订阅了另一个 Topic。

初步猜测：**Rebalance 在计算队列分配时，把所有消费者实例都纳入了计算，但实际只有部分实例在消费该 Topic，导致分配给"不消费"实例的队列无人处理。**

## 源码确认：Rebalance 分配规则

为了验证猜测，我们来看 RocketMQ 客户端的 Rebalance 源码。

### Rebalance 触发

`RebalanceService` 是一个后台线程，默认每 20 秒执行一次 Rebalance：

```java
// RebalanceService.java
public void run() {
    while (!this.isStopped()) {
        this.waitForRunning(waitInterval); // 默认 20000ms
        this.mqClientFactory.doRebalance();
    }
}
```

除了定时触发，当消费者上下线时，Broker 也会主动通知该消费者组中的所有消费者立即执行一次 Rebalance。Broker 端通过 `DefaultConsumerIdsChangeListener` 监听消费者变化事件：

```java
// DefaultConsumerIdsChangeListener.java (Broker 端)
public void handle(ConsumerGroupEvent event, String group, Object... args) {
    switch (event) {
        case CHANGE:
            List<Channel> channels = (List<Channel>) args[0];
            if (channels != null && brokerController.getBrokerConfig().isNotifyConsumerIdsChangedEnable()) {
                for (Channel chl : channels) {
                    // 向该消费者组的所有客户端发送通知
                    this.brokerController.getBroker2Client().notifyConsumerIdsChanged(chl, group);
                }
            }
            break;
        // ...
    }
}
```

客户端收到通知后，会唤醒 `RebalanceService` 线程立即执行 Rebalance，而不用等待 20 秒的定时周期：

```java
// ClientRemotingProcessor.java (客户端收到 Broker 通知)
public RemotingCommand notifyConsumerIdsChanged(ChannelHandlerContext ctx, RemotingCommand request) {
    final NotifyConsumerIdsChangedRequestHeader requestHeader = ...;
    log.info("receive broker's notification[{}], the consumer group: {} changed, rebalance immediately",
        RemotingHelper.parseChannelRemoteAddr(ctx.channel()),
        requestHeader.getConsumerGroup());
    this.mqClientFactory.rebalanceImmediately(); // 唤醒 RebalanceService 线程
    return null;
}

// MQClientInstance.java
public void rebalanceImmediately() {
    this.rebalanceService.wakeup();
}
```

总结一下，Rebalance 的触发有两种方式：
1. **定时触发**：每 20 秒自动执行一次（兜底机制）
2. **事件触发**：消费者上线或下线时，Broker 主动通知该组所有消费者立即 Rebalance（保证及时性）

### 为什么在客户端做 Rebalance

RocketMQ 选择在客户端而非服务端做 Rebalance，这是一个重要的架构决策。

**为什么不在 Broker 端做？**

- Broker 是消息存储和转发的核心节点，如果再承担队列分配的职责，会增加 Broker 的复杂度和负载
- 在分布式场景中，Broker 可能有多个节点，如果由 Broker 来做分配，还需要在多个 Broker 之间协调，增加一致性维护的难度
- 客户端 Rebalance 让 Broker 保持无状态（对于分配关系而言），Broker 只需要提供"当前有哪些消费者"这一信息即可

**为什么不会错乱？**

虽然每个客户端独立做 Rebalance，但不会出现"两个消费者争抢同一队列"或"某个队列没人消费"的情况（在订阅关系一致的前提下）。关键在于分配算法的**确定性**：

```java
// RebalanceImpl.java
List<MessageQueue> mqAll = new ArrayList<>(mqSet);
Collections.sort(mqAll);   // 所有客户端看到相同的队列列表（排序后）
Collections.sort(cidAll);  // 所有客户端看到相同的消费者列表（排序后）

// 使用相同的确定性算法进行分配
List<MessageQueue> allocateResult = strategy.allocate(
    this.consumerGroup,
    this.mQClientFactory.getClientId(),
    mqAll,
    cidAll
);
```

只要满足以下三个条件，所有客户端计算出的分配结果就一定是一致的（不会冲突）：
1. **相同的输入**：所有客户端从 Broker 获取到相同的消费者列表（cidAll）和队列列表（mqAll）
2. **相同的排序**：对队列和消费者都做了排序，保证顺序一致
3. **确定性算法**：分配算法是纯函数，相同输入一定产生相同输出

每个客户端各自计算"我应该消费哪些队列"，虽然是独立计算，但由于输入和算法完全相同，最终得到的全局分配结果也完全一致——这就是客户端 Rebalance 不会错乱的根本原因。

> 当然，在极短的时间窗口内（比如某个消费者刚上线，各客户端收到通知的时间有先后），可能会出现短暂的分配不一致。但这只会导致某个队列短暂地被两个消费者同时拉取，RocketMQ 通过消费幂等和 offset 提交机制来容忍这种瞬态不一致，最终会收敛到一致状态。

### 核心逻辑：rebalanceByTopic

在 `RebalanceImpl.doRebalance()` 中，会遍历当前消费者订阅的所有 Topic，对每个 Topic 分别调用 `rebalanceByTopic()` 进行队列分配：

```java
// RebalanceImpl.java
public void doRebalance(final boolean isOrder) {
    Map<String, SubscriptionData> subTable = this.getSubscriptionInner();
    if (subTable != null) {
        for (final Map.Entry<String, SubscriptionData> entry : subTable.entrySet()) {
            final String topic = entry.getKey();
            this.rebalanceByTopic(topic, isOrder);
        }
    }
    this.truncateMessageQueueNotMyTopic();
}
```

`rebalanceByTopic()` 在集群模式下的关键逻辑：

```java
// RebalanceImpl.java - CLUSTERING 模式
case CLUSTERING: {
    // 1. 获取该 Topic 的所有队列
    Set<MessageQueue> mqSet = this.topicSubscribeInfoTable.get(topic);

    // 2. 从 Broker 获取该消费者组的所有消费者 ID
    List<String> cidAll = this.mQClientFactory.findConsumerIdList(topic, consumerGroup);

    if (mqSet != null && cidAll != null) {
        List<MessageQueue> mqAll = new ArrayList<>(mqSet);
        Collections.sort(mqAll);
        Collections.sort(cidAll);

        // 3. 使用分配策略计算当前消费者应该分配到哪些队列
        AllocateMessageQueueStrategy strategy = this.allocateMessageQueueStrategy;
        List<MessageQueue> allocateResult = strategy.allocate(
            this.consumerGroup,
            this.mQClientFactory.getClientId(),
            mqAll,
            cidAll
        );
        // ...
    }
}
```

### 关键问题：Broker 返回的消费者列表

`findConsumerIdList()` 最终调用 Broker 端的 `getConsumerListByGroup`：

```java
// ConsumerManageProcessor.java (Broker 端)
public RemotingCommand getConsumerListByGroup(...) {
    ConsumerGroupInfo consumerGroupInfo =
        this.brokerController.getConsumerManager().getConsumerGroupInfo(
            requestHeader.getConsumerGroup());
    if (consumerGroupInfo != null) {
        List<String> clientIds = consumerGroupInfo.getAllClientId();
        // ...
    }
}
```

而 `getAllClientId()` 的实现如下：

```java
// ConsumerGroupInfo.java
public List<String> getAllClientId() {
    List<String> result = new ArrayList<>();
    Iterator<Entry<Channel, ClientChannelInfo>> it = this.channelInfoTable.entrySet().iterator();
    while (it.hasNext()) {
        Entry<Channel, ClientChannelInfo> entry = it.next();
        ClientChannelInfo clientChannelInfo = entry.getValue();
        result.add(clientChannelInfo.getClientId());
    }
    return result;
}
```

**注意：这里返回的是该消费者组中所有注册的消费者 ID，没有按 Topic 过滤！**

### 队列分配算法（AllocateMessageQueueAveragely）

默认的平均分配算法逻辑如下：

```java
// AllocateMessageQueueAveragely.java
public List<MessageQueue> allocate(..., List<MessageQueue> mqAll, List<String> cidAll) {
    int index = cidAll.indexOf(currentCID);
    int mod = mqAll.size() % cidAll.size();
    int averageSize = mqAll.size() <= cidAll.size() ? 1
        : (mod > 0 && index < mod ? mqAll.size() / cidAll.size() + 1
                                   : mqAll.size() / cidAll.size());
    int startIndex = (mod > 0 && index < mod) ? index * averageSize
                                               : index * averageSize + mod;
    int range = Math.min(averageSize, mqAll.size() - startIndex);

    for (int i = 0; i < range; i++) {
        result.add(mqAll.get((startIndex + i) % mqAll.size()));
    }
    return result;
}
```

简单来说，就是把所有队列按照消费者数量平均分配，每个消费者负责一段连续的队列。

## 为什么会堆积：同 Consumer Group 不同 Topic

有了上面的源码分析，现在来还原问题场景：

### 场景

```
Consumer Group: order_group

Consumer1 (实例A): 订阅 topic_order
Consumer2 (实例B): 订阅 topic_order
Consumer3 (实例C): 订阅 topic_pay（不订阅 topic_order）
Consumer4 (实例D): 订阅 topic_pay（不订阅 topic_order）
```

### 问题产生过程

1. **Consumer1 对 topic_order 做 Rebalance 时**：
   - 从 Broker 获取 `order_group` 的所有消费者：`[Consumer1, Consumer2, Consumer3, Consumer4]`（4个）
   - `topic_order` 的队列：`[Queue0, Queue1, Queue2, Queue3]`（4个）
   - 平均分配：每个消费者分 1 个队列
   - Consumer1（index=0）分到 Queue0

2. **Consumer2 对 topic_order 做 Rebalance 时**：
   - 同样获取全部 4 个消费者
   - Consumer2（index=1）分到 Queue1

3. **Consumer3 和 Consumer4**：
   - 它们没有订阅 `topic_order`，所以不会执行 `topic_order` 的 Rebalance
   - 但它们在 Broker 的消费者组注册表中占了位置

4. **结果**：
   - Queue2 被"分配"给了 Consumer3，但 Consumer3 根本不消费 `topic_order`
   - Queue3 被"分配"给了 Consumer4，但 Consumer4 根本不消费 `topic_order`
   - **Queue2 和 Queue3 无人消费 → 消息堆积！**

这就是为什么我们看到只有 2 个队列在正常消费，另外 2 个队列的 Offset 完全不动。

## 类似问题：同 Topic 不同 Tag

除了不同 Topic 导致的问题，同一 Topic 但不同 Tag 也可能引起类似的问题。

### 场景

```
Consumer Group: order_group

Consumer1: 订阅 topic_order, tag = "TagA"
Consumer2: 订阅 topic_order, tag = "TagB"
```

### 问题分析

RocketMQ 的消费者通过心跳向 Broker 上报订阅信息。由于同一个消费者组只维护一份 `subscriptionTable`，后注册（或心跳更新更频繁）的消费者会覆盖前面的订阅关系：

```java
// ConsumerGroupInfo.java
public boolean updateSubscription(final Set<SubscriptionData> subList) {
    for (SubscriptionData sub : subList) {
        SubscriptionData old = this.subscriptionTable.get(sub.getTopic());
        if (old == null) {
            this.subscriptionTable.putIfAbsent(sub.getTopic(), sub);
        } else if (sub.getSubVersion() > old.getSubVersion()) {
            this.subscriptionTable.put(sub.getTopic(), sub);
        }
    }
    // ...
}
```

这里 `subscriptionTable` 的 key 是 Topic 名，所以同一个 Consumer Group 对同一个 Topic 只会保留最后一次更新的订阅关系（Tag 过滤条件）。

**后果**：
- 如果 Consumer2 的心跳后到达 Broker，那么 Broker 上记录的 `topic_order` 的 Tag 过滤就变成了 `TagB`
- 当 Consumer1 拉取消息时，Broker 用 `TagB` 做服务端过滤，`TagA` 的消息在服务端就被过滤掉了
- 反之亦然，取决于心跳到达的顺序

最终的效果是：**部分消息可能永远不会被消费**，要么是 TagA 的消息被丢弃，要么是 TagB 的消息被丢弃。由于心跳的覆盖是不确定的，表现为消费"抖动"——时而 TagA 的消息能消费到，时而消费不到。

## 原则：订阅关系一致性

通过上面的分析，我们可以总结出一个核心原则：

> **同一个 Consumer Group 下的所有 Consumer 实例，必须保持订阅关系完全一致。**

"订阅关系一致"包含三层含义：

| 维度 | 要求 | 违反后果 |
|------|------|----------|
| **Consumer Group** | 同一个 Group 的消费者必须订阅相同的内容 | Rebalance 分配错乱 |
| **Topic** | 所有实例必须订阅完全相同的 Topic 集合 | 部分队列无人消费 → 堆积 |
| **Tag** | 对同一 Topic 的 Tag 过滤条件必须一致 | 服务端过滤条件被覆盖 → 丢消息 |

### 正确示例

```java
// 所有消费者实例代码一致
consumer.subscribe("topic_order", "TagA || TagB");
consumer.subscribe("topic_pay", "*");
```

### 错误示例

```java
// 实例A
consumer.subscribe("topic_order", "TagA");

// 实例B（同 group，但订阅不同）
consumer.subscribe("topic_order", "TagB");  // Tag 不一致！
consumer.subscribe("topic_pay", "*");       // Topic 集合也不一致！
```

## 排查建议

遇到消息堆积时，可以按以下步骤排查：

1. **查看消费者组的连接情况**：通过 RocketMQ Console 或 `mqadmin consumerConnection` 命令查看该 Group 下所有消费者实例的订阅信息，确认是否一致。

2. **检查队列分配**：通过 `mqadmin consumerStatus` 查看每个队列被分配给了哪个消费者，如果发现某些队列的分配消费者不在实际消费该 Topic，则基本可以确认是订阅不一致导致的。

3. **检查代码**：确认所有使用该 Consumer Group 的代码，`subscribe()` 调用是否完全一致（包括 Topic 和 Tag）。

4. **修复方案**：
   - 保持同 Group 下所有消费者的订阅关系完全一致
   - 如果业务确实需要不同的订阅关系，使用不同的 Consumer Group

## 总结

消息堆积的原因有很多，但"订阅关系不一致"是最隐蔽、最容易被忽略的一种。它的根本原因在于 RocketMQ 的 Rebalance 机制——Broker 返回的消费者列表是按 Group 维度获取的，不区分该消费者实际订阅了哪些 Topic。这导致分配算法会把队列"分配"给不消费该 Topic 的实例，造成部分队列无人消费。

牢记一点：**同一 Consumer Group = 同一订阅关系**，这是 RocketMQ 的使用前提。
