# 聊聊Java25中的虚拟线程，可用了吗

上篇 [聊聊 Java 21 虚拟线程——我为什么觉得它对业务开发没那么大用](https://mp.weixin.qq.com/s/HiqbWG586sWYHoTlxghwgQ) 中，我们说了，如果只是为了用虚拟线程，没必要专门为这个升级JDK到Java21，评论区有支持的，有反对的，其中有一条是因为上篇说的是Java21，那不可避免的要提Java21中的synchronized导致的pin问题，有不少人说Java25中解决了（实际上Java24就解决了，甚至如果你用了自研JDK，比如AJDK，在Java21中就给解决了），那也不能说Java25中解决了，Java21里边的这个问题就不能提了；

不过既然如此，那我们不妨换一个角度来讨论：

> 现在，有必要为了虚拟线程专门升级到 Java 25 吗？

我的答案依然和上一篇差不多：

对于绝大多数业务系统而言，没有太大的必要。至少，“仅仅为了虚拟线程”去升级 Java 25，这件事的收益并没有你想象中那么高。

如果你确实打算升级，那么建议先认真考虑下面几个问题。

## 关于线程切换开销问题

很多人提到：

- 平台线程（物理线程）切换成本高
- 虚拟线程切换几乎没有成本

这当然是事实。

但问题在于：你的系统真的已经被线程切换拖垮了吗？

如果你的服务流量并不大，那么线程切换带来的损耗，很多时候根本不是主要矛盾。

而如果你的业务已经大到需要考虑虚拟线程，比如秒杀、高并发网关、超大规模 IO 场景，那通常意味着你已经做过充分压测，并且 CPU 利用率已经压到 90% 甚至 95% 以上。

在这种情况下，线程切换开销能占多少？

5%？  
7%？

如果再高，那往往说明程序本身已经存在其他明显问题。

换句话说：

即使你把线程模型从平台线程完全切换为虚拟线程，并且假设虚拟线程切换“零开销”，最终带来的收益可能也只有几个百分点。

而现实中：

- 优化一次慢 SQL
- 减少一次不必要的数据库访问
- 降低一次远程调用
- 优化缓存命中率

带来的收益，通常都比“换线程模型”更直接、更明显。

> 如果你连压测都没做，或者 CPU 利用率还远远没到瓶颈，那其实还没到该认真考虑虚拟线程的时候。  
> 先把现有系统优化到极限，往往比换技术栈更有价值。

## 不可忽视的成本问题

当然，有可能你们公司规模非常大。

对于你们公司来说，哪怕 3%～5% 的资源节省，长期来看都是一笔巨大的收益。

但问题在于：

线程模型的变化，从来不只是“升级一下 JDK”这么简单。

你原本所有的优化，包括：

- JVM 参数调优
- 线程池模型
- 框架行为
- 中间件配置
- 自研组件设计

本质上都是基于“平台线程”这个前提建立的。

一旦切换到虚拟线程，很多东西都要重新验证：

- 升级框架
- 改造自研框架
- 重构部分业务代码
- 做全链路回归测试
- 做全链路压测
- 重新调优 JVM 与中间件参数

真正做过这种升级的人都知道：

这里面投入的人力、时间和资源，其实是非常夸张的。

而且更现实的问题是：

你还需要说服领导愿意为这件事投入资源。

## 关于背压问题

虚拟线程还有一个很容易被忽视的问题：背压。

以前使用平台线程时，线程池大小可能只有：

- 300
- 500
- 1000

这天然就形成了一层并发限制。

但换成虚拟线程之后，由于线程变得“很便宜”，很多人会把并发直接放大到：

- 3000
- 5000
- 甚至更多

问题也随之而来：

你的下游系统，真的能扛住么？

原本一个服务最多同时打 1000 个请求给下游，现在突然变成 5000 个，下游如果没有做完善的限流、隔离、熔断，很可能直接被打挂。

当然，你可以通过连接池来限制并发。

但现实情况是：

你很难保证所有地方都正确配置了连接池。

甚至有些原本“不需要连接池”的地方，在虚拟线程时代也不得不重新考虑资源隔离问题。

因此，虚拟线程并不只是“提升吞吐量”这么简单，它实际上也会导致一些隐形的更致命的问题。

## 最关键的稳定性问题

如果你的系统并发已经大到必须依赖虚拟线程来提升资源利用率，那么此时最重要的事情，其实不是性能，而是稳定性。

在大型互联网公司里，有两句非常现实的话：

> 稳定性压倒一切。  
> 你可以不做，但不能做错。

尤其是从 Java 8、11、17等以前的老版本升级上来时，很多时候已经不只是 JDK 升级，而是整个技术栈的升级：

- Spring 版本升级
- 中间件升级
- 字节码工具升级
- Agent 兼容性验证
- 监控体系调整
- GC 行为变化

这些都会带来额外风险。

很多线上事故，往往不是因为“新技术不好”，而是因为“系统复杂度已经远超预期”。

还有一句更现实的话：

> 省下来的钱是公司的，出了问题背锅的是自己的。

这也是为什么很多公司在技术升级上会格外保守。

## 最后

当然，这并不是说虚拟线程不好。

恰恰相反，我认为它是 Java 近些年最重要的特性之一。

尤其对于新项目而言：

直接使用 Java 25，并基于虚拟线程构建系统，我认为完全没问题，而且很可能是更好的选择。

因为虚拟线程确实能够：

- 让同步编程重新变得优雅
- 干掉异步回调的复杂度
- 提高代码可读性
- 更自然地处理 IO 密集型任务

有些场景甚至天然适合虚拟线程，比如 JDBC。

过去为了避免阻塞，我们不得不：

- 使用回调
- 使用响应式编程
- 拆分大量异步逻辑

而现在，很多逻辑终于可以重新回到“顺序代码”的写法。

这本身就是非常大的价值。

另外，如果是公司层面统一推动技术栈升级，有完整的人力、测试、运维体系配合，那当然也值得做。

但如果只是个人“觉得虚拟线程很先进”，于是想为了它单独升级整套系统，那我只能说慎重；
